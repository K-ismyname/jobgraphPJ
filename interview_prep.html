M0 한 줄 피치 ▶
핵심 공식

문제 → 해결책 → 차별점 (40초 오프닝)

문제: 기존 플랫폼은 점수만 주고 근거가 없다

해결책: 실제 공고 데이터 + 코드·배포 교차검증

차별점: 적합도와 신뢰도를 분리해서 보여줌

예상 질문
❓ "이 프로젝트를 간단히 소개해주세요." ▶
채용공고를 수집·분석해 이력서를 올리면 직무 대비 갭과 개선 방향을 알려주는 Agentic RAG 시스템입니다. 기존 서비스가 점수만 주는 것과 달리, "이 스킬이 부족하다"는 주장이 공고 텍스트와 GitHub 코드로 실제로 뒷받침되는지를 신뢰도 등급으로 분리해 보여줍니다.
M1 왜 만들었나 ▶
핵심 설명

단순 키워드 매칭: "Python 잘 함"이 이력서에 있으면 무조건 통과 → 근거 없음

LLM이 "이 주장이 코드/배포로 확인되는가?"를 판단

신뢰도를 적합도와 분리 — 점수와 근거를 구분해 다룸

예상 질문
❓ "이 프로젝트를 만든 계기가 뭔가요?" ▶
취업 준비 중 이력서 점수 서비스를 써봤는데 "왜 부족한지"에 대한 근거가 전혀 없었습니다. 공고를 직접 분석하고 코드와 배포로 검증하면 근거 있는 갭 분석이 가능하다고 판단해 만들었습니다.
❓ "기존 채용 플랫폼과 어떻게 다른가요?" ▶
기존 서비스는 이력서 텍스트만 보고 점수를 냅니다. 이 시스템은 ① 실제 공고 데이터를 수집해 직군별 요구 스킬을 파악하고, ② GitHub 코드와 배포 URL로 주장을 교차검증해, ③ 적합도(몇 개 충족)와 신뢰도(그 주장이 얼마나 확실한가)를 분리합니다.
M2 아키텍처 큰 그림 ▶
6개 레이어
수집(L1) → Neo4j(L2) → LangGraph 에이전트(L3) → 갭 분석(L4) → RAGAS 평가(L5) → FastAPI(L6) 데이터 흐름: 이력서 PDF → 4개 평가자 병렬 → 교차검증 → gap 루프(최대 5회) → 코칭 → 최종 리포트

원칙: 뒤 레이어를 앞 레이어보다 먼저 짜지 않는다 — API 서버는 에이전트 완성 후, 평가는 기능 완성 후

예상 질문
❓ "시스템 아키텍처를 설명해주세요." ▶
6개 레이어로 나눴습니다. Adzuna API로 공고를 수집해 Neo4j 그래프에 저장하고, LangGraph 에이전트가 이력서·GitHub·배포 URL을 병렬로 평가한 뒤 교차검증합니다. 갭 분석 루프가 근거를 찾고, RAGAS로 품질을 측정하며, FastAPI로 서빙합니다.
❓ "어떤 순서로 개발했나요? 왜 그 순서인가요?" ▶
데이터 없이는 에이전트를 테스트할 수 없고, 에이전트 없이는 API를 의미 있게 만들 수 없습니다. 그래서 수집→저장→에이전트→분석→평가→서빙 순으로 진행했습니다. 뒤 레이어를 앞보다 먼저 짜지 않는 원칙을 명시적으로 정해두었습니다.

예상 질문
❓ "왜 LangGraph를 선택했나요?" ▶
이 시스템에는 세 가지가 필수입니다: 조건 분기(증거 충분한가?), 루프(부족하면 다시 검색), HITL(애매한 경우 사용자에게 되묻기). LangChain 체인만으로는 이 세 가지를 동시에 구현할 수 없습니다. LangGraph의 StateGraph가 정확히 이 용도입니다.
❓ "벡터 DB를 안 쓴 이유가 뭔가요?" ▶
처음에 Chroma를 도입했는데, 검색 12건을 직접 실행해서 키워드 매칭 결과와 비교했습니다. 11건이 동일한 결과였고, 1건도 실질적 차이가 없었습니다. 복잡도만 올라가고 효과는 없어서 제거했고, Neo4j 그래프 쿼리로 대체했습니다.
M4 핵심 설계 의사결정 ★ ▶
5개 결정
1. 적합도 ⊥ 신뢰도 분리
적합도(fit): 직군 핵심 스킬 중 몇 개 보유 (코드로 계산)
신뢰도: 그 주장이 얼마나 믿을 만한가 (Verified / Corroborated / Claimed)
→ "Python 잘 함(이력서 주장)" ≠ "Python 잘 함(GitHub 확인)"
2. 결정적 계산 — LLM이 숫자를 못 만들게
consensus.py, critic.py는 LLM 없이 코드로만 동작
LLM은 숫자를 지어낸다 → 신뢰도 등급은 규칙 기반으로 산출
3. 다중 소스 교차검증 (4개 평가자 병렬)
resume / github / portfolio / deploy 독립 평가 후 합의
이력서 주장만 믿으면 과장이 걸러지지 않음
4. Corrective RAG 루프
근거가 부족하면 tools를 다시 호출 (최대 5회)
에이전트가 스스로 "증거가 충분한가?"를 판단 → 부족하면 재검색
5. Critic = 판단 없는 서기
Gap 리포트 ↔ Consensus 대조해 환각만 제거
적합도 판단은 Gap 루프에 위임, Critic은 라벨 교정만 (역할 분리)
예상 질문
❓ "RAG 구조를 어떻게 설계했나요?" ▶
검색 소스를 벡터 유사도가 아니라 Neo4j 그래프 쿼리와 GitHub API로 구성했습니다. 에이전트가 근거를 검색하고, "이 근거가 충분한가?"를 스스로 판단해서 부족하면 다시 검색합니다(Corrective RAG). 최종 리포트의 각 주장은 어느 공고에서 근거를 가져왔는지 출처가 붙습니다.
❓ "환각(hallucination)은 어떻게 처리했나요?" ▶
두 단계입니다. ① Critic이 Gap 리포트의 스킬 목록과 Consensus(실제 평가 결과)를 대조해서 Consensus에 없는 스킬 주장을 제거합니다. ② 신뢰도 등급은 LLM이 아닌 규칙 기반 코드로 산출해서 LLM이 임의로 등급을 만들 수 없게 막았습니다.
M5 LangGraph 에이전트 상세 ▶
흐름도
입력 → evaluator_dispatch ↓ [Send API — 병렬 fan-out] resume_eval | github_eval | portfolio_eval | deploy_eval ↓ (모두 완료 후) consensus → seed_gap ↓ [루프, 최대 5회] call_model ↔ tools(verify_skills, graph_query …) ↓ synthesizer → critic ↓ [루프, 최대 3회] coach → finalize_coach → END
예상 질문
❓ "병렬 처리는 어떻게 했나요?" ▶
LangGraph의 Send API를 사용했습니다. evaluator_dispatch 노드에서 활성화된 소스(이력서·GitHub·포트폴리오·배포) 각각에 Send를 발행하면, LangGraph가 이를 병렬로 실행합니다. 모두 완료된 후 consensus 노드로 합류합니다.
❓ "루프는 언제 멈추나요?" ▶
gap 루프는 MAX_ITERATIONS(5회) 카운터로 제한합니다. LLM이 "증거 충분"으로 판단하거나 5회가 되면 종료됩니다. 코치 루프도 별도로 최대 3회입니다.

❓ "코드에서 LLM 의존성을 줄인 곳이 있나요?" ▶
consensus.py와 critic.py가 대표적입니다. 신뢰도 등급 산출과 환각 제거를 LLM이 아닌 규칙 기반 코드로 구현했습니다. LLM이 숫자나 라벨을 만들면 임의성이 생겨서 같은 입력에 다른 신뢰도가 나올 수 있기 때문입니다.

예상 질문
❓ "RAGAS 지표 결과가 어떻게 됩니까? Faithfulness가 낮은 이유는?" ▶
Faithfulness 0.250, Answer Relevancy 0.876입니다. Faithfulness가 낮은 건 구조적 한계입니다. Adzuna 공고가 "required" 명시 없이 "familiarity with X is a plus" 같은 간접 표현을 써서 NLI 매칭이 어렵습니다. 이 한계를 알고 있기 때문에 개선 방향(공고 텍스트 품질 향상, structured 근거 포맷)도 제시할 수 있습니다.
❓ "벡터 검색 없이 어떻게 RAG인가요?" ▶
RAG의 핵심은 외부 소스에서 증거를 검색해 LLM 답변을 보강하는 것입니다. 벡터 유사도 검색이 유일한 방법이 아닙니다. Neo4j 그래프 쿼리와 GitHub API·배포 URL 검색이 검색 역할을 합니다. 오히려 그래프 쿼리는 관계 기반 검색이 가능해서 "LangGraph를 쓰면 LangChain도 씀" 같은 생태계 연관 스킬도 찾을 수 있습니다.
❓ "Chroma 제거 측정 데이터가 있나요?" ▶
검색 12건을 직접 실행해 결과를 키워드 매칭과 비교했습니다. 11건이 동일한 결과, 1건도 실질적 차이 없음을 확인했습니다. 효과 없음을 데이터로 증명한 뒤 복잡도 추가 없이 제거를 결정했습니다.
